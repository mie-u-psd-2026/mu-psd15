このガイドについて

どのファイルが何をしているか、講義で何を学んだかを一箇所にまとめたページです。

アプリは クレトレ(クレーム対応トレーニング)。AIが怒った顧客を演じ、利用者は店員として応対します。応対の良し悪しが怒りの数値として動き、終了後にAIが講評します。

アクセス先http://localhost:5001

最初から入っていたひな型は何ができたか

テキストを1つ入力して送ると、AIが返事を返すだけの最小のアプリでした。「関西弁で実行」ボタンは、AIへの指示文を差し替えると応答が変わることを示す見本です。この仕組みが、クレトレの「顧客を演じさせる」土台になっています。

ファイルごとの役割

中身を知らなくても、どこに何が書いてあるかが分かるようにしています。

app.py — サーバー側 配布

ブラウザからのお願いを受け取り、AIに問い合わせて、結果を返します。大きく4つのまとまりでできています。

行のあたりまとまりやっていること
1〜70設定使うAIの名前、3つの事例の定義、怒りの上限や目標値
70〜150小さな部品AIへの問い合わせ、返答の読み取り、終了判定
150〜2603つのAPIブラウザからのお願いを受ける窓口
260〜324起動処理AIを温めてからサーバーを立ち上げる

大事な数値はすべて先頭にまとまっています。ここを書き換えるだけで動きが変わります。

RESOLVED_ANGER  = 15   ← ここまで下げたら成功
MAX_TURNS       = 12   ← 何回やり取りできるか
MAX_ANGER_DELTA = 12   ← 1回で動く怒りの上限

static/index.html — 画面側 配布

1つのファイルに、見た目(HTML)・装飾(CSS)・動き(JavaScript)がすべて入っています。ファイルを分けていないのは、規模が小さく、分けるほうが分かりにくくなるためです。

場所中身
<style> の中色や余白の指定。先頭の :root に色をまとめてある
<section> ×3準備・会話・結果の3画面。v-if で切り替える
<svg>お客さんの顔。眉・目・口を怒りの値で動かす
<script> の中データの保持、APIの呼び出し、画面の切り替え

requirements.txt 配布

このアプリが動くのに必要な部品(ライブラリ)の一覧です。pip install -r requirements.txt と打つと、ここに書かれたものが一括で入ります。バージョンまで固定してあるので、誰の環境でも同じものが入ります。

.gitignore 配布

Gitに入れてはいけないファイルを書いておく場所です。秘密の情報、自動生成される巨大なフォルダなどを除外します。

.env            ← APIキーなど秘密の情報
__pycache__/    ← Pythonの中間ファイル
*.pyc
.venv/          ← ライブラリ置き場(巨大)

動く仕組み

ボタンを押してから返事が出るまでに何が起きているか。

1. ブラウザ  「返答する」ボタンを押す
              ↓  POST /api/turns  (会話の履歴と今の怒りの値を送る)
2. app.py    AIへの指示文を組み立てる
              ↓
3. Ollama    顧客のセリフと怒りの値を作る
              ↓  【怒り】72
                 【セリフ】返品対応してくれる？
4. app.py    返答から数値とセリフを取り出す
             1回で12以上動かないよう制限する
             終わりかどうか判定する
              ↓  {"anger":72, "message":"...", "status":"continue"}
5. ブラウザ  怒りメーターを動かし、セリフを吹き出しで表示
覚えておく役はブラウザ

会話の履歴と怒りの値はブラウザが持っています。サーバーは何も覚えず、毎回まとめて受け取ります。この作りにするとデータベースが要らなくなり、作るものが減ります。

3つのAPIの窓口

窓口いつ使う返ってくるもの
POST /api/conversations練習を始めるとき顧客の第一声と初期の怒り
POST /api/turns返答を送るたび新しい怒りの値と顧客のセリフ
POST /api/reviews会話が終わったとき3観点の点数と講評

名前が動詞ではなく名詞なのは、Day3で学んだRESTの決まりに合わせているためです。

要件定義・プロジェクト管理

Day4 ／ 9月3日(木)

開発・クリーンコード・バージョン管理

  • コードは書く時間より読まれる時間のほうが長い
  • 意図が伝わる命名。単位を名前に含める(delayMs)。真偽値は is has で始める
  • 関数は10〜20行。ガード節で入れ子を浅くする
  • コメントは What ではなく Why を書く
  • DRY(繰り返さない)・KISS(簡単に)・YAGNI(今要るものだけ)
  • AIの出力を理解せずコピペしない。最終責任は自分にある
  • Gitの4領域、ブランチとPull Request、コンフリクトの解消
  • コミットメッセージの接頭辞(feat: fix: docs:)
作品への反映

main に直接コミットせず、ブランチを切ってPull Requestでマージする運用に変更。コミットメッセージに接頭辞を付けた。__pycache__ を .gitignore に追加。

アプリの起動方法

3つ打つだけです。

cd /Users/hayato/source/mu-psd15
.venv/bin/python app.py

起動したらブラウザで http://localhost:5001 を開きます。止めるときはターミナルで Ctrl + C を押します。

初めて動かすとき、または他のパソコンで動かすとき 
python3 -m venv .venv                    ライブラリ置き場を作る
.venv/bin/pip install -r requirements.txt 必要な部品を入れる
ollama pull gemma2:9b                     AIをダウンロード(5.4GB)

うまくいかないとき

症状原因と対処
ポート5001が使用中前のサーバーが残っている。lsof -tiTCP:5001 | xargs kill
返事が20秒以上かかるAIがメモリから外れている。サーバーを再起動すると温め直される
「サーバーにつながりません」python app.py が動いていない

Gitの使い方

この授業で使う操作だけに絞っています。

いつもの流れ

git switch -c feature/やること名   1. 作業用の枝を作る
   … ファイルを編集する …
git add .                          2. 変更をまとめる
git commit -m "feat: 何をしたか"    3. 記録する
git push -u origin feature/やること名  4. GitHubへ送る
gh pr create                       5. 合流を申請する

コミットメッセージの接頭辞

接頭辞使うとき
feat:新しい機能を足した
fix:不具合を直した
docs:書類だけを変えた
refactor:動きは変えずコードを整理した
